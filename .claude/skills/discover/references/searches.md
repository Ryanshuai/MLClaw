# The searches — what to look for, where, and what a finding is worth

The sweep in `SKILL.md` Step 2 is the data-shaped instance of one pattern. This file is the pattern, written out per source and per subject, so the same engine can be pointed at data, at somebody's recorded results, or at credentials and machines without a second implementation and a second set of statuses.

Read this before adding a search. **The thing that makes the engine generic is already in the script and is easy to break**: two axes, kept apart.

## The two axes, and why they are not the same

| Axis | Field | Answers |
|---|---|---|
| Where the claim came from | `source_type` | how much the mention is worth before anybody looks |
| Where the thing is | `on` | which probe goes and looks |

`discover.py` already separates these — `--source-type code` with `--on s3` is the normal case, and it is the most valuable one in a takeover: *the code that ran named a bucket*. Collapsing them (probing "the source") loses exactly that: a bucket named in a config that ran and a bucket named on a wiki page get the same probe and must not get the same credence.

So a search is specified as a pair: **which sources to mine for candidate locations**, and **which probe classifies them**.

## What each subject needs found

The engine is subject-agnostic; what differs is the target list. For data and weights that list comes from the stage's declared needs — `input.json → items` and `artifacts.json → items` are literally "what this code requires", and `candidates` is "what is actually here". Discovery is the loop that fills the second from the first, plus a sweep for what nobody declared.

| Subject | Target list | Lands in |
|---|---|---|
| **data** | `input.json → items`, plus anything a sweep turns up that nothing declared | `candidates`, then `/data-check` declares and censuses |
| **weights** | `artifacts.json → items` | `candidates` + `items.<n>.origin` |
| **results** | one per published/inherited artifact whose number is claimed but unmeasured | `output.json → baseline` (eval), run history (training), perf fields (infer) |
| **credentials + compute** | what a probe needed and did not have — this list is *generated by the other searches failing* | `resources.json` |

The last row is why credential discovery belongs in this engine rather than beside it. A missing AWS key is not the substrate under discovery, it is the most common **finding** of discovery: every `unreachable` names what was missing, and that set *is* the credential worklist. Splitting it out means the W&B key and the W&B runs — one fact — become two records that drift.

## Sources, ranked by what a mention is worth

Work down. Do not start at the wiki. The ranking is the same for every subject; only the patterns change.

### code — a path a script read is a path that existed

| Subject | Patterns |
|---|---|
| data | data roots, `Dataset` classes, config YAMLs, `--data-dir` defaults, docker mounts, `.env` files |
| weights | `load_state_dict`, `from_pretrained`, checkpoint globs, `resume_from` |
| results | `wandb.init(entity=, project=)`, `mlflow.set_tracking_uri`, `SummaryWriter(log_dir=)`, and the env vars that hold the same (`WANDB_PROJECT`, `MLFLOW_TRACKING_URI`) |
| creds | committed keys — `grep -rIE '(AKIA|ghp_|sk-|xox[bp]-|-----BEGIN)'`, and `*_setup_env.sh` / `Makefile` / CI YAML |

**Committed credentials are a finding, not a convenience.** Record the lead, name the file, and do not put the value in the record — `discovery/leads.json` is git-tracked, so a key copied into it is a key committed twice. This is the same split as `rig.json → host.server` and `/ask-human`'s contact details: the record holds the *key name and location*, never the material.

### git history — a removed path is evidence of data that existed and moved

`git log -S<path>`, `git log --diff-filter=D`, deleted config files, and commit messages, which carry intent no config does (`revert aug, hurts mAP 2pt`). For results this is often the only surviving record of a metric: a number quoted in a commit message or a deleted README table.

**A rotated credential leaves its history behind.** `git log -S` on a key prefix finds keys that were removed from HEAD and are still in the pack — which is a live exposure and a lead worth recording as such.

### tracking backend — a run that trained recorded what it read

The highest-value source for results, and the only one that carries both halves at once: a run's `config` names the data and hyperparameters, its `summary` names the number. For data leads it yields paths that provably fed a training run.

**Ten backends, and the split that matters is whether probing needs access.** `TRACKING` in `discover.py` is the table.

| Family | Probe | Backends |
|---|---|---|
| **disk** | marker glob under a path — no import, no network, **no credential** | `tensorboard`, `mlruns`, `lightning`, `wandb_local`, `aim`, `dvclive` |
| **service** | credential → package → listing | `wandb`, `mlflow`, `clearml`, `neptune`, `comet` |

**Probe the disk family first**, and not for tidiness: it is the only tracking history readable before access arrives, which is the state a handover begins in. `train-init` Step 0 already ranks it that way — local leftovers are a default-yes because they need no key.

The service family stages, and each stage is its own answer: no credential (a worklist entry, never an absence) / credential but no adapter / the server answered and the project is not there (`gone`) / reachable with N runs.

**Prefer a REST surface over a vendor package when a backend offers both**, and this is a correctness argument rather than a preference: urllib needs nothing installed, so the listing runs on the bare interpreter a handover starts with *and* can be tested against a stub server. `mlflow`, `clearml`, `neptune` and `comet` all go that way. `wandb` publishes no REST surface of the same kind, so it is the one backend left on the package path — which is also why it is the one that needed a real account to exercise.

| Backend | Auth shape | Exercised against |
|---|---|---|
| `mlflow` | `Authorization: Bearer` (optional) | a stub **and a real server** |
| `wandb` | its SDK reads `~/.netrc` | **a real account** — 25 runs on one project, a 10-project entity listing |
| `clearml` | Basic → `auth.login` → Bearer, and it needs **both** halves of the key pair | a stub |
| `neptune` | `X-Neptune-Api-Token` → oauth exchange; the token is base64 JSON **carrying the host**, so decoding it is how self-hosted deployments are found | a stub |
| `comet` | the key raw in `Authorization`, no `Bearer` scheme | a stub |

**A stub proves the parsing and the dispatch, not the endpoint** — so the property that carries the three unexercised ones is narrower and it is the one enforced: *being wrong about a URL, an auth scheme or a body shape can only ever produce `unreachable`.* A 200 whose body does not parse is `unreachable` saying `NOTHING WAS COUNTED`; only a listing that succeeded and did not contain the name may say `gone`. A false `gone` would tell somebody their history was deleted because this file guessed a path wrong, and that is the one error nobody walks back — they stop looking.

A backend with no listing adapter must state **both halves**: that a key was found, and that nobody counted. Either half alone sends the reader the wrong way. No shipped backend is in that state now; the branch is where a *new* one lands, which is why its check drives a synthetic backend rather than naming a real one that will grow a listing next month.

### servers / S3 / cloud console — listings are evidence, not assertions

Walk **one level**. A sweep that spends four hours on a NAS is a sweep nobody runs twice, and the budget rule below exists for the same reason.

### docs / wikis — somebody wrote it, possibly from memory, possibly years ago

Everything found here is `claim` and stays `claim` until a probe agrees. Query by project / repo / dataset name; never crawl a space. Two things doc sources are uniquely good for, and no other source has them: **the reason a thing exists**, and **numbers nobody logged**.

A handover page is the canonical instance — including the case where the page is itself at risk (a personal wiki space, a departing account). **A source that will stop being reachable on a known date is not an ordinary `claim`**: it is a claim with an expiry, and the sweep has to say so, because the ordinary response to "unreachable, come back when access arrives" is wrong when access is about to be revoked instead of granted. Record it with `--access-expires-at`.

### people — the last resort and often the only one

`/ask-human`, and their answer is a `claim` until something else agrees. `outsourcing` parties are never probed: a vendor may hold the only copy of a batch, and they are a source of **answers**, not listings.

## Probes, by `on` — and the fussiness is the point

A probe's job is to reach one of four verdicts honestly. The failure that matters is a false `gone`: it sends somebody chasing data that is fine, and buries the one real loss in the noise.

| `on` | Verdict rules | Built? |
|---|---|---|
| `local` | missing path → `gone`. `PermissionError` / `OSError` → **`unreachable`**, never `gone` — the single most common source of a false `gone`. Walk bounded by a time budget; over budget → size "not measured", never a partial total | yes |
| `server:<key>` | no such key in `resources.json`, or no host/alias → `unreachable`. ssh failure → `unreachable`. Path absent while the host answered → `gone`. **Requires both a zero exit and a sentinel**, because a shell that dies mid-command returns zero and an empty listing | yes |
| `s3` | Credential comes from **`resources.json → aws`**, not from whatever the CLI resolves ambiently — see below. `aws` not installed, or anything mentioning credentials / expiry / access → `unreachable`, and the blocker distinguishes **`s3:denied_with_registered_key`** (a policy ask) from **`s3:no_usable_credential`** (a key ask). `gone` when the listing genuinely ran and returned nothing: exit 1 **plus** the `--summarize` sentinel `Total Objects: 0` **plus** empty stderr. This is the one place `gone` is a reading rather than a guess | yes |
| `tracking:<backend>` — disk | path missing, or listed and holding no markers → `gone` (a real reading, same bar as an empty S3 prefix). Not a directory → `unreachable` | yes, **and executed** |
| `tracking:<backend>` — service | no credential → `unreachable`, naming which env vars and config files checked. No adapter/package → `unreachable`, and it says a key *was* found. A 200 whose body does not parse → `unreachable`, `NOTHING WAS COUNTED`. `gone` only when the server itself listed and the project was not in it | all five; `mlflow` and `wandb` against real servers, three against stubs |
| unknown `on` | `record` refuses at write time; `probe` says no probe was dispatched rather than guessing one | yes |
| `cloud_console`, `doc`, `person` | not probeable by machine. These stay `claim` and are resolved through `/ask-human` | n/a |

**Every `unreachable` must name what was missing**, in the words a person can act on ("no AWS credentials", "host P608 did not answer", "private repo"). That text is the credential worklist; a bare `unreachable` produces a lead nobody can clear.

**A probe resolves the credential the registry declares, and says which one it used.** `resources.json` is the declaration every run skill reads through, so a probe that resolves something else is answering about a different world than the one a run will execute in. This was got wrong once and the shape of the failure is worth keeping: `probe_server` read `resources.json → servers` while `probe_s3` shelled out to a bare `aws s3 ls` and inherited the ambient credential. On a real handover those were two different IAM users — the registry held a key that could list the buckets, the ambient default could not — so the sweep reported `unreachable` over 12 GB of readable training data and put *go get an S3 key* at the top of a worklist for a key that was already registered.

Two things made it survive. It never produced a false `gone`, so the answer stayed inside the safe band while being wrong about the world — **a safe wrong answer is harder to notice than an unsafe one.** And `sources` computed its s3 row from `resources.json` while the probe did not, so the checklist called the source usable on the strength of a credential nothing then used. Hence the standing rule: **the checklist reports the credential the probe will use, resolved by the same function.**

**The last four characters, never the material.** `leads.json` is git-tracked, so a probe names `resources.json -> aws.access_key_id (…Q3GM)` — enough to tell two keys apart, which is the whole question when a probe is refused, and nothing more. Same rule as the committed-credentials row above.

## Where the vocabulary breaks, and it is not cosmetic

For a location, `verified` means *something other than a sentence listed it and it is there*. Carry that word onto a result and it silently changes meaning.

A W&B run whose summary says `mAP 48.5` gives a lead that is **`verified` as a record and `claimed` as a number.** The probe confirmed that the assertion exists and was made by a machine; it confirmed nothing about the model. Writing `verified` there and letting a reader take it as "the number is verified" is a fake verification of precisely the shape guarded against elsewhere in this lifecycle — and it collides head-on with `artifacts.json → items.<n>.origin.confidence`, where `verified` means *somebody re-ran eval and the number reproduced*, which only a closed `/repro` session establishes.

Two words, same spelling, opposite bars. So:

- a result lead's status describes **the record**, never the number;
- when it lands in `output.json → baseline` it carries `confidence: claimed` regardless of how clean the probe was;
- and a `scope` is mandatory on the way in. A bare `mAP 48.5` is comparable to nothing, so a result lead without a scope is not a finding, it is a rumour with a decimal point.

## Cross-cutting rules, inherited and not negotiable

- **`--evidence` is not optional.** Six months on, nobody can tell which lead came from a config that ran and which came from a wiki page written from memory — and that difference is the whole basis for deciding which `gone` to panic about.
- **Re-probe on a clock.** An inherited repo is often still moving; every `file:line` goes stale the moment you pull. Default 7 days.
- **`exhaustive` is `false`, always.** A sweep finds what somebody wrote down or left a path to. Data nobody documented and no surviving code points at does not appear, and no number of clean probes changes that.
- **Report the gaps before any count.** Unprobed, unreachable and stale come first. A findings list with its caveats underneath gets read as an inventory.
- **Read-only, one level deep, never writes to a source.** Document connectors in particular usually carry write scopes next to the read ones; creating a page to answer a question about your own project modifies somebody else's system as a side effect.

## What this design still cannot say

One gap, kept on purpose. Three others were here and are closed; the record of what they were is kept, because each one was found by a method worth reusing.

1. **`unreachable` never becomes `gone` by itself, and it never will.** A probe must not conclude absence from its own blindness — that is the whole skill. What the expiry field adds is that the *unresolved-at-lapse* case gets a name (`access_expired_and_unresolved`), so a loss that has become permanent is visible as such instead of sitting in the pending pile looking like every other todo. The status still does not move, and nothing should make it.

2. ~~A lead has no expiry.~~ **Closed.** `record --access-expires-at` plus the two `report` sections it feeds.

3. ~~Nothing watches the date.~~ **Closed.** CLAUDE.md → "On Conversation Start" step 4 now reads both sections and reports them *ahead of* unprobed and unreachable. The ordering is the point, and it is the only entry on that list with a **deadline** rather than a staleness: an unarchived day can still be copied tomorrow, a stale census re-scanned, an unprobed lead keeps waiting — a key that rotates on the 14th does not. `SomethingWatchesTheExpiryDate` in `contract_discover.py` joins the halves, because a computed section nobody opens is precisely the failure the field was added to prevent.

4. ~~`sources` under-reports what could have been swept.~~ **Closed**, and it was worse than under-reporting. With nothing registered it returned a single row — *resources.json is missing* — so a project whose git history and on-disk tracking leftovers were sitting there unread looked like a project with nothing to read. Those are the credential-free sources, the only ones available in the weeks a handover actually starts in, so the verb read as an argument for waiting. It now lists every family ranked above, each row carrying `kind` (mine / probe / ask) and `blocked_by` (**credential** / **human** / registration / absent) — because "blocked" alone routes a wiki page to the same queue as an expired AWS key, and no credential ever unblocks a wiki page.

**How these were found, since the method transfers.** The general question — "what is missing from this design" — produced nothing. What produced all three was asking what the record would have to say to save *one specific number* that *one specific account's* deactivation was about to take with it, and then asking who would ever read the answer. The first question yields a field; the second yields the thing that opens it.
